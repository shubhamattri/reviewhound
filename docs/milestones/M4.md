# M4: proof by a failing test

## What was built

- `config.py`: `proof` section (`enabled: false`, `min_severity: blocker`, `runner: docker|local`,
  `timeout_s: 60` (1..600), `max_findings: 3` (0..20), `downgrade_unproven: false`), strict.
- `src/reviewhound/proof.py` (new):
  - `ProofAnswer` (pydantic): `test_path` must be a relative `test_*.py` path with no `..`, no
    leading `-`, only `[A-Za-z0-9_./-]`; `code` non-empty; optional `expected_exception`.
  - `build_proof_prompt`: finding, enclosing function (tree-sitter index), whole file (capped
    at 20 KB), module import path. Asks for a test that asserts the correct behaviour.
  - `SandboxRunner` protocol; `LocalRunner` and `DockerRunner`. Both write the head snapshot
    plus the test into a fresh `mkdtemp` and always remove it in `finally`.
  - `parse_junit` (defusedxml, report capped at 5 MB because the code under test can write
    it) and `classify` -> proven / not_proven / inconclusive.
  - `run_proof_stage`: eligibility (verified, severity >= min, model-sourced, Python, capped),
    attach `proof`/`proof_test`/a note, optional downgrade, re-apply the posting floor, recompute
    the verdict. Never raises.
- `findings.py`: `Finding.proof` and `Finding.proof_test`.
- `poster.py`: proven findings say "**Proven:**" and fold the test into `<details>` with a
  fence longer than any backtick run in the test; body-only lines get "(proven by a failing test)".
- `pipeline.py`: `Reviewer(..., proof_runners=...)`, a timed `proof` stage after policy, only
  when `proof.enabled`. Wrapped so a proof failure never fails the review.
- `cli.py`: `--allow-local-proof` (operator opt-in for the local runner) and `--proof-image`.
- `evals.py` / `evals/build_cases.py`: recorded proof answers, `expected_proofs`, two cases.
- README: config, how proof works, and the danger of running PR code.

Classification rules: any junit `<error>` (collection, syntax, fixture) -> inconclusive; any
skip -> inconclusive; all pass and exit 0 -> not_proven; every test failed with `AssertionError`
or the claimed exception (never Import/ModuleNotFound/Syntax/Indentation/TabError) and exit 1 ->
proven; mixed pass/fail, other exception, odd exit code, timeout, missing/unparseable report,
runner error -> inconclusive. The exception type comes from the junit failure text's final
`path:line: ExcType` line (pytest drops the type from the message for rewritten asserts when
our ini is used; seen in a real run, kept as `assert_stripped.xml`).

## Independent review (fresh reviewer agent, read-only)

Fixed from it:
- A test could plant `junit.xml` as a FIFO (hang) or a symlink (to /dev/zero, or to a host file).
  Now opened with `O_NOFOLLOW | O_NONBLOCK`, must be a regular file, read at most cap+1 bytes.
- `expected_exception="builtins.ImportError"` bypassed the ban list (the full string was checked
  but only the suffix was allowed). The suffix is now normalised before the check.
- A crash mid-stage could leave a downgraded finding with a stale REQUEST_CHANGES verdict. The
  floor and verdict are now re-applied in a `finally`.

Accepted and documented (see Risks), not fixed:
- Any exception the model names counts, and a wrong expected value in an assert also "proves".
  Nothing checks that the traceback passes through the changed code.
- The junit report and exit code come from the same process as the untrusted code. A repo
  `conftest.py` can forge "proven" or force a pass.
- LocalRunner: the code under test can read `/proc/<ppid>/environ` on Linux (same uid). A
  repo-supplied `resource.py` runs before the rlimits are applied. There is no RLIMIT_NPROC.
  Background children survive a normal exit.
- Docker: directories created by root in `/out` may not be removable by the host user, so
  `_remove_tree` logs a warning and the temp dir leaks.

## Not done

- TypeScript proofs: next step is a vitest/jest runner behind `SandboxRunner`; out of scope.
- Docker path never ran against a real daemon (none on this machine); tested with a fake command
  runner only. The default `python:3.12-slim` image has no pytest, so out of the box every Docker
  proof is inconclusive until the operator passes `--proof-image` with pytest installed.
- Proof verdicts are not persisted in the store (only on the in-memory `Finding`, notes and the
  posted comment).
- On macOS `RLIMIT_AS` cannot be set, so LocalRunner has no memory cap there (CPU and file size
  still apply). A test that calls `setsid` can escape the process-group kill; LocalRunner is not a
  sandbox and is documented as trusted-repos-only.
- No retry of a malformed proof answer (spec: inconclusive).

## Risks for whoever merges

- `pipeline.py`, `config.py`, `findings.py`, `poster.py`, `cli.py` are edited by other milestones
  in parallel; conflicts are likely at the `Reviewer.__init__` signature and `_comment_body`.
- `test_pipeline.py`'s exact stage-set assertion is untouched because the `proof` stage only
  appears when enabled; a merge that always times the stage would break it.
- Proof model calls go through the same `ProviderRegistry`, so proof-call failures count toward
  that provider's circuit breaker.
- `downgrade_unproven: true` lets PR code influence severity (a passing test downgrades a blocker).
  Default off; README says so.
- Recorded eval now spawns two real pytest subprocesses (cases 13/14), adding about 1-2 s.
- "proven" is evidence, not certainty. PR code runs in the same process that writes the report,
  so a malicious PR can forge any verdict. The only verdict a PR author gains from forging is
  "not_proven", which matters only with `downgrade_unproven: true`.
- LocalRunner is not a sandbox. With `--allow-local-proof`, a PR can read the server's
  environment through /proc on Linux.
