# Milestone 3: GitHub App and feedback loop

## What was built

- **GitHub App auth** (`src/reviewhound/vcs/github_app.py`, new). `GitHubApp` signs an RS256 JWT
  (`iss` = app id, `iat` = now - 60s, `exp` = now + 540s) and trades it for an installation token
  via `POST /app/installations/{id}/access_tokens`. Tokens are cached per installation until 5
  minutes before `expires_at`. 429/5xx and transport errors are retried (3 attempts); 4xx is not.
  A malformed response raises and caches nothing. `GitHubApp.from_env()` reads
  `REVIEWHOUND_APP_ID` and `REVIEWHOUND_APP_PRIVATE_KEY_PATH`: neither set means no App, one set
  or an unreadable/invalid key is a `GitHubAppConfigError`. The key, JWT and tokens are never
  logged and `repr()` shows only the app id. `token_for_job()` picks the job's installation
  token when an App is configured, else the static token. Dependency: `pyjwt[crypto]`.
- **Token provider in `GitHubVCS`**: `token` may be a `str` (unchanged path) or a
  `Callable[[], str]` called per request and per git checkout, so an expired installation token
  is replaced transparently. An empty token from the provider raises `GitHubError`.
- **Installation id on jobs**: nullable `installation_id` column, added in place to existing
  queue DBs (`ALTER TABLE` inside `BEGIN IMMEDIATE`, so two processes opening an old DB do not
  race). The webhook stores `installation.id`; a redelivery with an id updates it, one without
  keeps it. A non-integer id is a 400.
- **Per-job worker auth**: `run_one`/`run_forever` accept a `Reviewer` or a factory
  `Callable[[Job], Reviewer]`. Factory errors are classified like any other job failure. The CLI
  worker uses the factory when App credentials are set, the old single reviewer otherwise.
- **Feedback loop** (`src/reviewhound/github_feedback.py`, new):
  - after a review is posted and recorded, read back `GET /repos/{r}/pulls/{n}/reviews/{id}/comments`
    and store `comment id -> fingerprint` in `comment_links` (matched by file and line; one
    comment per line is already a policy rule);
  - `pull_request_review_thread`: `resolved` -> `resolved`, `unresolved` -> `reopened`, for every
    linked comment in `thread.comments`;
  - `pull_request_review_comment` `created` with `in_reply_to_id` on one of our comments ->
    `reply` with the body cut to 500 chars. Replies with `performed_via_github_app.id` equal to
    `REVIEWHOUND_APP_ID` are ignored. Each reply is applied once (`feedback_events` key); if the
    write fails the key is released so a redelivery can apply it;
  - unknown comment ids are ignored and logged with the ids;
  - the webhook does DB writes only.
- **Stale verdict**: after a posted review with no open blocker, every earlier posted
  `REQUEST_CHANGES` review of ours on the PR that has no successful dismissal is dismissed via
  `PUT /repos/{r}/pulls/{n}/reviews/{id}/dismissals`. "Open blocker" includes a blocker held as
  "already posted on an earlier head" (still present, just not re-posted); a blocker the
  developer resolved or declined does not count. Each attempt is written to `dismissals`
  (`ok`, `error`); a failure is logged, recorded, retried after the next posted review, and
  never fails the review. Follow-ups run only after the review row is written.
- **Docs**: README "Install as a GitHub App"; example `app-manifest.json`.

## Not done, and why

- **Comments on deleted lines**: out of scope (owned by another developer; `checker.py`/`diff.py`).
- **Live App install on the sandbox**: the brief forbids GitHub write calls and network; every
  GitHub call is tested against `httpx.MockTransport` only. The endpoint shapes follow GitHub's
  REST docs but have not been exercised against github.com.
- **Feedback for a `post-uncertain` review**: no post id, so its comments are never linked and
  thread events on them are logged as unknown.
- **Thread event dedupe**: a redelivered `resolved` writes a second identical feedback row (state
  is unchanged). Replies are deduped by comment id.
- **Retry on 401 with a fresh token**: not added; the 5-minute margin makes expiry mid-request
  unlikely, and the job retries on the next attempt anyway.

## Risks for whoever merges

- `pipeline.py`: if the post stage is refactored in parallel, keep `after_post` after
  `_finish` (the review row must be written before any follow-up side effect).
- `queue.py`: if another branch changes `_SCHEMA` or `Job`, keep `installation_id` as the last
  `Job` field with a default, and keep `_migrate()` in `__init__`.
- `qa/github_qa.py` builds a `Reviewer` with a real `GitHubVCS` and a store, so a QA run now
  also reads back comments and may dismiss an earlier REQUEST_CHANGES review it posted on the
  sandbox PR. That is the intended behaviour, but it is a new GitHub write in QA.
- A review posted with a user token cannot always be dismissed by the App (or the reverse) if
  the identity changes between heads; that shows up as a recorded failed dismissal, not an error.
- `GitHubApp` holds its lock during the token HTTP call, so a slow exchange for one installation
  delays token reads for others in the same process. The worker is single-threaded today.
